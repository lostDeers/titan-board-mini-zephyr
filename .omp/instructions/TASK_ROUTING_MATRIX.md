# Task Routing Matrix

Use this matrix after reading `AGENTS.md` and before editing. Select the strictest applicable route for mixed tasks, but split host-testable logic from hardware-only behavior when that reduces risk.

| Task type | Triggers | Required route | Required evidence | Forbidden shortcut |
| --- | --- | --- | --- | --- |
| Research / report | Codebase investigation, design critique, workflow review, compatibility report without implementation. | Read relevant files and references directly. Use `/hardware-compatibility` for new hardware feasibility. | File paths, commands, references, or observations used. | Do not build, flash, debug, or write code unless explicitly requested. |
| Hardware compatibility exploration | New display, sensor, radio, storage, shield, connector, SoC peripheral, or module feasibility before implementation. | `/hardware-compatibility`. | Verdict, evidence, integration sketch, risks/unknowns, smallest later validation step. | Do not mark Implemented, Built, Flashed, Runtime Verified, or complete. |
| Source-only firmware change | Pure logic, parsers, protocol encoders/decoders, register-layout helpers, shared-memory layouts, small host-independent refactors. | `/host-test` when feasible, then `/embedded-review` for meaningful C/C++/headers. | Narrow host/unit test command and PASS/FAIL; review findings. | Do not use hardware build success as a substitute for host-testable logic coverage. |
| Refactor planning | Requested refactor where scope, public API impact, module boundary, behavior invariants, or verification path is not yet clear. | `/refactor-plan`. | Refactor class, invariants, callsite map, affected contracts, verification plan, risks, rollback path, and confirmation needs. | Do not edit or claim improvement before the plan is approved. |
| Refactor execution | Mechanical/internal refactor, or approved public API/module-boundary/hardware-sensitive refactor. | `/refactor`, then `/host-test` when feasible, then `/embedded-review` for meaningful embedded changes; hardware-sensitive refactors use the hardware behavior route. | References/callsites checked, affected contracts updated, tests/builds run, review findings, and generated config/DTS/map/ELF inspection when relevant. | Do not hide behavior changes under a refactor label or leave old/new APIs partially cut over. |
| Hardware behavior change | Drivers, DTS/Kconfig affecting peripherals, IRQ/DMA/cache, board bring-up, display/audio/sensor/storage/network behavior. | Build -> `/embedded-review` -> flash -> `/hardware-debug` or direct runtime verification -> `/record-evidence`. For multi-candidate experiments, review and flash-gate each candidate separately. | Build output, generated `.config`/`zephyr.dts`/ELF/map as relevant, per-candidate review gate (`cleared`, `experimental only`, or `blocked`), flash Program/Verify, runtime observations, warning triage. | Do not claim hardware behavior from build or flash alone. Do not apply a cleared review verdict from one candidate to another overlay/config/driver variant. |
| Zephyr build failure | `west build`, CMake configure, Kconfig, Devicetree, generated header, linker, or memory-region failure. | `/zephyr-build-fix`. | Failing command, root cause, minimal files changed, rebuild PASS/FAIL, warnings. | Do not suppress warnings or change runtime behavior beyond the build root cause. |
| Target runtime diagnosis | Flash/runtime failures, faults, hangs, missing logs, probe/RTT/UART issues, IRQ/DMA/cache behavior, physical effects. | `/hardware-debug`. | Target context, artifact, commands, logs/registers/counters/signals, status from `STATUS_AND_EVIDENCE.md`. | Do not keep debugging after destructive hardware action would be required without approval. |
| Host tooling / scripts | Build/flash/debug/monitor scripts, conversion tools, host-side automation. | Syntax/dependency check and dry-run or actual run. Use `/embedded-review` when target workflow is affected. | Command output, PASS/FAIL, printed target/build/artifact context, cleanup behavior. | Do not hide logs or use broad destructive process/file operations without justification. |
| Docs / memory / evidence | README, docs, memory files, evidence records, status claims, user-facing reports. | `/embedded-review` when documents state hardware status or verification. `/record-evidence` after observations unless no-modification mode applies. | Exact status vocabulary, evidence links or candidate evidence, warning triage, and confirmation that user-facing `docs/` content is sanitized. | Do not upgrade status beyond observed evidence. Do not write unredacted personal data, local absolute paths, private SDK/toolchain paths, probe serials, hostnames, user prompts, workflow instructions, credentials, or session artifacts into user-facing `docs/`. Do not maintain unredacted reports or sensitive/local artifacts in git. Workflow policy files may document this rule. |
| Reference material / copied vendor code | `references/`, copied vendor/reference code, provenance docs, active build inputs that might point at references. | `/reference-check`. | No active build dependency on `references/`, license/header preservation, origin path, adaptation notes, local API boundary. | Do not include, compile, link, or source files directly from `references/`. |
| Performance / streaming optimization | Camera, audio, display, storage, network, NPU, motor/sensor streaming, DMA producer/consumer paths. | `STREAMING_DMA_CACHE_CHECKLIST.md`, build/generated inspection, runtime metrics, `/embedded-review`, `/record-evidence`. | Baseline/current metric, overhead, cache/DMA/memory symbols, map/ELF placement, data correctness, bounded drops. | Do not compare metrics from different app paths or omit validation/logging overhead. |
| Git hygiene | Branch cleanup, staging, commit preparation. | `git status --short --branch`; inspect diffs; commit only when explicitly requested. | Intended files only; no build outputs, logs, binaries, SDK paths, credentials, session exports. | Do not stash, reset, checkout, clean, or discard user work without explicit approval. |

## Final Gate Checklist

1. Task classification is clear.
2. Required reads were completed.
3. Required tests/builds/runtime checks were run, or missing hardware evidence is explicitly classified.
4. Meaningful embedded changes were reviewed.
5. Warnings were triaged.
6. Evidence/current memory was updated when hardware evidence or status changed, unless the user explicitly forbade modifications.
7. No build outputs, generated binaries, local logs, SDK paths, credentials, session exports, unredacted reports, personal data, absolute local paths, private tool paths, probe serials, hostnames, user prompts, or workflow instructions are staged or maintained in `docs/`.
